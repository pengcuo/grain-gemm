# GB10 G256：CUTLASS 与 CuTe 剩余性能差距调查

本次找到了三个普通投影形状的可复现原因：当前 CUTLASS kernel 对合法 K 下界的表达影响了编译器的代码生成。只在设备端增加 `if (K < 256) return;`，保留原 CUTLASS Adapter、collective 和 epilogue 后，实验版在三个形状上反而比 CuTe 延迟低 1.35%–2.34%。因此，这些形状原先约 1% 的差距不能归为 CUTLASS 固有的框架成本。

对于当前项目，继续用直接 CuTe C++ 编写特化 kernel 是合理的工程选择：目前已经有可用实现，修改流水线、scale 调度和写回比较直接。但本次结果不支持“直接 CuTe 必然更快”。现有 CUTLASS 路径本身也是定制 collective，并非未经修改的通用 GEMM 模板。

本目录发布原始测量、审计与报告。消融改动仍作为独立实验保留，没有据此修改正式 kernel 或自动分配表。

**单项源代码改动与机器码证据**

[正式 host launcher](../../../../src/grain_gemm/kernels/csrc/grain_cutlass.cu#L49) 已要求 K 为正且是 256 的倍数，但这项 host 检查不等于设备编译器获得同样的范围信息。[实验代码](../../../../experiments/cutlass/variants/minimum_k_guard/grain_cutlass_kernel.hpp#L68) 在读取 K 后、任何预取之前增加：

```cpp
if (K < 256) return;
```

对合法输入，这个检查不改变计算语义。在 CUTLASS cfg15（128×128 tile、3 stages、256 threads）上，SASS 对比显示：

- 初始化区域少了 31 条 CS2R 清零指令；追踪 64 个 FP32 累加寄存器，原有效路径上的两次清零变为一次。
- 主循环回跳范围内的静态指令数从 447 变为 429。循环内 CS2R 数量不变；变化主要在地址、索引和控制指令，包括部分 stage 索引从普通寄存器转入 uniform 寄存器。
- Tensor Core IMMA、INT32→FP32 转换、scale 算术、主要数据搬运和循环同步次数不变；寄存器仍为每线程 250 个，没有 spill。

这建立了“显式 K 下界 → 编译结果改变 → 这些形状性能改善”的可重复证据。它不能把全部收益进一步分摊给清零或某一种指令：同一个源代码改动同时影响初始化和循环调度，且 cfg11 同样减少清零却没有加速。

**独立复测结果**

GB10，CUDA 13.0；INT8 输入、G256、FP32 scales/累加、BF16 输出。下面每个单元格为 **延迟 μs / 等效 TFLOPS**，等效吞吐按 `2*M*N*K/time` 计算，INT8 运算本质上是整数 TOPS。只测预量化后的 GEMM，包括分组缩放和写回，不含量化、编译或 host 分配/调度。

“原 CUTLASS”是减少实例化数量的对照库，对应三个配置的完整 SASS 与正式库相同；正式库也参与每轮测量，作为独立负对照。全部结果取 run3。

| M | N | K | CuTe μs / TOPS | 原 CUTLASS μs / TOPS | K 下界实验版 μs / TOPS | 实验版相对 CuTe 延迟变化 |
|---:|---:|---:|---:|---:|---:|---:|
| 1024 | 1024 | 1536 | 28.12 / 114.56 | 28.26 / 113.98 | 28.30 / 113.84 | +0.59% |
| 1024 | 1536 | 1024 | 24.74 / 130.21 | 25.03 / 128.67 | 24.29 / 132.59 | -1.88% |
| 1024 | 2048 | 1536 | 48.33 / 133.29 | 49.10 / 131.22 | 47.17 / 136.57 | -2.34% |
| 2048 | 1536 | 1024 | 50.24 / 128.23 | 51.07 / 126.15 | 49.57 / 129.97 | -1.35% |
| 2048 | 151936 | 1536 | 6841.95 / 139.71 | 7033.31 / 135.91 | 7015.06 / 136.26 | +2.74% |

延迟是 60 个轮次中位数的中位数；最后一列是同轮次延迟比的中位数，与两列总体中位数相除可能略有不同。负值表示实验版延迟更低。固定配置分别为 CuTe/CUTLASS：第一行 3/11、中间三行 7/15、最后一行 15/23，不经过调参筛选。

三个 cfg15 形状在上一次 run2 中也比 CuTe 延迟低 1.99%、2.25%、1.63%。run3 中三个形状的五个完整、位置平衡的 12 轮块都复现了优势。

**其他单项实验与剩余问题**

| 单项改动 | 实测结果 | 判断 |
|---|---|---|
| 删除直接写回路径尾部的等待和 barrier | LM head 在三次测量中相对原 CUTLASS 降低约 0.6% 延迟；run3 降低 0.56%，仍比 CuTe 慢 2.27% | 解释一部分，未解释全部 |
| 将共享写回循环改为编译期固定次数 | cfg11 略快约 0.2%，三个 cfg15 形状反而慢约 0.4%–0.7%（run1） | 多余线程范围检查确实消失，但不能据此推断整体更快 |
| 改用 CuTe 风格的 32-bit 线性输出地址表达式 | 差异接近负对照波动 | 未发现稳定收益 |
| 把 FP32 清零从 bridge 移到 collective 预取后 | 三个配置完整 SASS 与原版一致 | 没有形成有效机器码改动 |
| 特化掉 K>4096 的 grouped traversal 分支 | 没有消除三个 cfg15 形状的差距；cfg11 在 run2/run3 中略快于 CuTe 0.15%/0.18% | 作用依赖配置；小 K 时原复杂分支本就跳过，特化仍会改变其他代码的生成，不能把收益解释成省掉了实际执行的复杂分支 |

cfg11 原约 0.5% 的差距在本次分支特化实验中已经消除，但具体机制未获得完整因果解释；0.15%–0.18% 的微小领先也不宜外推。LM head 仍有约 2%–3% 差距未解释。资源审计排除了这些匹配配置中的额外 scale 算术、local-memory spill，以及寄存器差异导致的 resident CTA 数量变化；不能据此断言所有硬件瓶颈均相同。

Nsight Compute 的实际探测被硬件计数器权限拒绝（`ERR_NVGPUCTRPERM`），因此没有用 stall、issue utilization 或寄存器 bank 冲突计数来定位周期级原因。本次结论停留在已验证的源码改动和机器码变化，不猜测具体 stall 类型。

**测量与正确性检查**

同一形状各路径使用同一组输入、scale、输出缓冲区和相同 CUDA Graph 节点数。固定配置，预热 2 秒，60 轮交错执行，每轮每路径 3 次 CUDA event 测量。run1/run3 每条路径在每个执行位置出现 10 次；run2 为 8/9 次，截取前 56 个严格平衡轮次后结论保持一致。没有锁时钟，记录了温度与频率；同设备会话和相同数据 seed 的重复实验不代表跨机器复现。配对与位置平衡减轻漂移影响，不能消除所有相关性。

计时形状使用 32×32 采样参考比较和全输出 finite 检查，采样最大误差为 0；这不是大矩阵全量逐元素验证。另用包含 INT8 极值、逐行/列/组变化和正负/零 scales 的专用样例完成全输出参考验证，覆盖 K=256/768/1280/4352、三个配置；适用实验路径的 memcheck 与 racecheck 均为 0 errors/hazards。仅支持 K≤4096 的分支特化版本正确拒绝 K=4352。

独立 CPU 审计通过：15 个 case、95 条路径记录、17,100 次原始 replay 测量的统计、配对比值、源码和动态库哈希均匹配。bootstrap 区间只描述本轮数据，存在相邻轮相关性和多重比较限制，不用窄区间宣称微小差异在任意环境成立。

详细证据：[原始统计 CSV](results_run3.csv)、[独立审计结果](paired-audit.json)、[计时脚本](../../../../experiments/cutlass/archive/paired_benchmark.py)、[静态机器码分析](static-report.md)、[累加器清零追踪](positive-k-clear-evidence.json)、[正式源码和动态库未变更记录](production_unchanged.json)。静态分析文件中的候选原因由本报告的实测结论更新。
